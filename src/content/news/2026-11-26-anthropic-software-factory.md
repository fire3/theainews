11 月 25 日至 26 日，两份材料前后脚出现，拼出了一个少见的剖面：一家前沿实验室自己是怎么用 AI 写软件的。

一份是 The Pragmatic Engineer 的播客访谈，嘉宾是 Anthropic 平台工程负责人 Katelyn Lesse——她此前在 Stripe 带工程团队，现在负责 Claude API，以及 Claude Code、Claude Desktop 背后的基础设施。另一份是 Anthropic 工程博客同日发布的迁移长文《Migrating our Messages API to Rust》。

两份材料讲的是同一件事：Anthropic 把承载全部 Claude 流量的 Messages API 从 Python 单体重写成 Rust，<strong>约五个月上线，全程没有停机，也没有冻结新功能</strong>；单请求 CPU 下降约 70%、内存下降超过 80%、首字延迟中位数下降约 20%。但真正值得读的不是这些结果，而是他们怎么说服自己「重写是对的」——在 AI 能一周写出核心路径的时代，瓶颈从写代码挪到了验证代码。

## 一个「请求转发器」怎么变成 CPU 大户

Messages API 建于 2023 年，当时 Anthropic 还是一家研究公司，写 Python 是因为研究代码基本都是 Python，API 能直接和研究、推理侧的库共用依赖。它最初简单到被一位工程师称为「基本就是个请求转发器」。

到 2025 年底，情况完全不同：每个请求都要校验、转成送给模型的 prompt、分词、过一遍安全分类器；模型逐个 token 吐出回复后，还要把 token 流分拣成文本、思考、工具调用，再计费、限流。Python 在每一次建对象、释放内存、切换任务时都留下开销。从 2024 年初到 2026 年秋，API 流量增长了约 <strong>1,800 倍</strong>。

其实 2024 年就有人提过换语言。当时的结论被另一位工程师一句话钉死：<strong>「我们不会用 Go 或 Rust 重写 API！」</strong>

团队的第一次尝试是常规做法——只把慢的部分用 Rust 重写。他们用 Rust 替换了模型输出的解析逻辑，CPU 降了 8% 到 10%，但每个 token 现在要三次穿越 Python 与 Rust 的边界，新增的复杂度吃掉了收益。这次失败的局部优化，反而成了后来整体重写的论据。

## 一周写出初版，五个月才敢上线

到 2026 年 5 月，Claude 已经写下 Anthropic 合并代码的八成以上。迁移项目里，Claude 用大约一周写出了 API 核心请求路径的第一版。

问题在于，Anthropic 自己的博客写得很直白：<strong>「瓶颈已经不是生成，而是验证。」</strong>（Verification, not generation, had become the bottleneck.）他们要迁移的是一个活着的系统，用户依赖的边界行为大量落在测试集之外，而「正确」没法用一句话定义。

先试测试。他们手上约有 700 个集成测试，但有两个致命问题。一是测试与 Python 实现耦合——测试在同一个进程里跑 Python API，用 Python 内存 mock 掉计费和限流，Claude 帮着改代码时也顺手改了测试，事后审计发现<strong>超过 100 处被削弱的断言</strong>。二是覆盖不全：光是 20 个二元开关就能组合出上百万种配置，每个跑一秒要 12 天，还不算 prompt 的变化。

于是他们用生产流量给自己判卷，也就是影子流量（shadowing）。这一步的难点不在搭管道，而在三个约束：

- Python 版本还在持续变化，parity 是移动靶；
- Claude 的回答本身不确定，同一请求两次输出不同，差异不等于 bug；
- 不能读用户的请求和回复，所以没法直接看两边到底哪里不一样。

解法是只跑一次模型，把模型输出重放给 Rust——两边拿到同一份模型输出，剩下的差异就全是 API 层的事。至于隐私，他们不看文本，只记录<strong>差异的形状</strong>：先用 checkpoint 定位到哪一步、prompt 的第几段，再用「起点字节 + 长度差」组成的指纹（fingerprint）区分不同 bug。一个 bug 会在每条受影响的请求上留下相同指纹，于是几十万条近乎重复的记录可以被折叠成几类问题。

结果相当扎心：4 月时 Rust 版本能通过约 98% 的测试，但在生产流量上只有约四分之一（24%）的输入与 Python 完全一致；5 月初修一批问题后反而掉到 6.5%，因为前面的差异挡住了后面的差异；到 8 月才升到 99.6%。

*图：横轴是 2026 年 4 月到 8 月，纵轴是两边输入完全一致的比例。5 月初的下坠不是退化，而是前面的大差异修掉后，原本被遮住的小差异开始显形；6 月的两次回落来自 Rust 侧的改动。（来源：Anthropic 工程博客）*

## 三层验证环：快、真、以及别再犯

差异记录本身没有可读文本，只有一个指纹。Anthropic 的处理方式是让 agent 从指纹反推原因：猜一个根因，自己写一条能触发它的请求或模型回复，再跑两边比对。为此他们把流程拆成三个嵌套的环：

| 环 | 回答的问题 | 时延 | 卡点 |
| --- | --- | --- | --- |
| 内环 | 这次改动修好它了吗？ | 一秒以内 | 云沙箱里跑本地检查，输入检查不调模型，输出检查用假模型回放脚本 |
| 外环 | 生产上它真的消失了吗？ | 小时到天 | 工程师先审 PR，通过才部署，再用影子流量比较修前修后的指纹出现率 |
| 记忆环 | 为什么它反复出现？ | 随纠正到来 | 人的意见变成规则、lint、测试，写进 CLAUDE.md 供后续 agent 读取 |

从内环跨到外环的那道缝，就是人类把关的位置。博客里给了一个很能说明问题的例子：5 月中旬最大的剩余差异来自联网搜索——生产版会从内部服务取搜索工具的描述，Rust 版还没接这个服务，导致 prompt 里缺了这段文本。一个 agent 提议把文本抄进文件让 Rust 读取，本地验证器立刻通过。但工程师驳回了它，因为上线前 Rust 仍然必须调用那个服务，这段捷径代码最终会被扔掉。

Anthropic 由此总结出一条值得所有做 agent 工程的人抄下来的话：<strong>验证器能告诉 agent 输出是否一致，但不能告诉它这个修法是否值得上线</strong>。这次驳回被写进记忆，随后帮 agent 把大量同类记录直接归并到已知问题，而不是各自再造一个绕行方案。

6 月，一个 agent 还把团队约 60 条 review 意见做了聚类，提出规则草案，由工程师编辑后写进 CLAUDE.md。

## 结果：不只快在数字上

9 月公开流量切到 Rust 后，三组指标一起动：单请求 CPU 降约 70%、内存降 80% 以上、首字延迟中位数降约 20%。合并进 Rust 代码的变更量也说明了节奏——4 月初每两周不到 100 个，6 月底接近 1,000 个，8 月中旬后的一个周期超过 3,000 个。

*图：灰色是 Python 份额、蓝色是 Rust 份额。延迟那条曲线在第一个点之前就开始下降，当时绝大多数请求还在 Python 上——说明迁移期间顺带做的优化也在起作用。（来源：Anthropic 工程博客）*

![三层验证环：内环问「这次编辑修好它了吗」，外环问「生产上没了吗」，记忆环问「为什么反复出现」](/images/2026-11-26-anthropic-software-factory/verification-loops.jpg)

## 组织侧：审查、oncall、面试、晋升都变了

播客里更值得关注的是流程本身的变化，因为这部分比数字更适合被别的团队借鉴或反驳：

| 环节 | 现在怎么运转 |
| --- | --- |
| 代码审查 | 一个 Claude 分类器处理所有 PR：判断是否需要人审、需要几个、该派给哪个团队。SDK 版本升级、换用更新模型、修 flaky test 这类机械改动，可以由另一个 Claude 互审后直接合并部署 |
| oncall | 一个 Claude agent 先于人类被「叫醒」，把告警分成真问题与噪声。长期目标是不用叫醒人，但尚未做到 |
| 入职 | 新人不再配对「onboarding buddy」，直接问连着代码库与内部系统的 Claude，它还能现场生成交互式教程 |
| 团队形态 | 仍是 5 到 8 人的两披萨团队。系统由团队负责、由团队被叫醒，不落到个人 |
| 规划 | 和 AI 之前相比没有缩短。跨推理、研究、安全、应用几个团队的拉齐，仍占掉大量时间，工程师花在协调上的时间比实现还多 |
| 工具 | 工程时间明显更多地流向自建工具。有人甚至自建了一个 Slack 频道，在里面跑一支多 agent 团队攻同一个目标，而这并不在他的任务清单上 |
| 面试 | 手写代码环节被取消——强候选人在其他环节表现很好，却栽在这一轮。目前实验中改成与编码 agent 一起做的面试，架构与项目深挖两轮不变 |
| 晋升 | 「项目完成时间」失去意义（原本一年的项目现在几天到几周），改看影响：省了多少 CPU、降了多少延迟、避免了多少事故 |

Lesse 对「技能贬值」的焦虑给了一个不太一样的回答，大意是：<strong>恰恰因为有 agent，围绕 agent 的基础设施问题才刚打开</strong>；多 agent 系统能不能解真正难的问题，取决于有没有人肯在这些领域深挖、形成判断。

## 该怎么读这份材料

两边都有立场。Anthropic 在卖 Claude，The Pragmatic Engineer 的节目有赞助商，而「工程师只细看了约 20% 的生成代码」是 Lesse 的估计，不是测量。这些不该被当成中立数据。

但 Anthropic 这篇博客的可信度比一般厂商材料高一些，因为它反常地公开了对自己不利的数字：98% 测试通过率只对应 24% 生产一致、指标一度跌到 6.5%、agent 提出的修法被工程师当场驳回。这类细节只有在真做过之后才写得出来。

还有一层背景值得放在这里：Anthropic 刚完成 IPO（发行价 83 美元），首周股价即跌破发行价，万亿美元市值承压。在这个时点强调「用十分之一的人做到同等规模」，既是工程叙事，也是资本市场叙事。

撇开立场，有一个结论是可以迁移的：<strong>能被廉价验证的项目，AI 才真的能接手</strong>。Messages API 之所以能被 AI 重写，不是因为 Claude 会写 Rust，而是因为有一个持续在生产中跑着的 Python 版本可以当判卷人，加上团队愿意花五个月建那套判卷系统。对没有现成 oracle 的项目，AI 只会更快地产生更多错误。

## 核心总结

- **事件**：Anthropic 用约五个月把承载全部 Claude 流量的 Messages API 从 Python 重写为 Rust，9 月切换公开流量，全程不停机、不冻结功能；单请求 CPU 降约 70%、内存降 80% 以上、首字延迟中位数降约 20%。
- **为什么要重写**：2023 年的「请求转发器」到 2025 年要承担校验、转 prompt、分词、安全分类、输出分拣与计费，流量在两年多里增长约 1,800 倍；先做的局部 Rust 化只省 8%–10% CPU，还引入每个 token 三次跨语言边界。
- **真正的难点**：Claude 一周写出核心路径初版，但 700 个集成测试与 Python 实现强耦合（审计发现 100 多处被削弱的断言），4 月测试通过率 98% 时生产输入一致率仅 24%，验证而非生成成为瓶颈。
- **方法论**：只跑一次模型、把输出重放给 Rust；不读用户数据，只记录差异的 checkpoint 与指纹；用内环（沙箱，秒级）、外环（影子流量，小时到天）、记忆环（人的纠正变规则与测试）三层闭环驱动 agent 修 bug。
- **组织变化**：Claude 分类器给 PR 分层决定人审数量与归属；oncall 由 agent 先分诊；入职直接问 Claude；两披萨团队保留；取消手写代码面试；晋升从「工期」改看「影响」。
- **关键结论**：验证器能判断输出是否一致，不能判断修法是否值得上线——人类的价值集中在内外环之间那道缝上。AI 能接管的是「可被廉价验证」的迁移，而不是所有工程。
