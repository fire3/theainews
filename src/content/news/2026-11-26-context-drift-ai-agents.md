2026 年 11 月 25 日，Google AI 的开发者关系工程师 Patrick Kelly 在 DEV Community 发布了一份实验报告，原文同步在他的个人博客上。他把一个带真实文件和终端工具的 git 仓库搭成编码沙箱，让 Gemini 3.8 Flash 与 Gemini Pro 跑了 <strong>470 个任务</strong>，并刻意埋入冗余上下文、重复规则、陈旧文档和直接矛盾的指令。

结论有个反直觉的转折：把上下文弄脏并不会让模型犯错，真正危险的是上下文之间互相打架——而<strong>模型多半发现了，却基本不会告诉你</strong>。

## 先分清：上下文腐烂与上下文漂移

这两个概念常被混为一谈，但成因完全不同。

- <strong>上下文腐烂（context rot）</strong>：Chroma 在[去年提出](https://research.trychroma.com/context-rot)的说法，指会话越来越长、塞满噪声、死胡同和干扰项之后，模型准确率下滑。
- <strong>上下文漂移（context drift）</strong>：团队的文件——`AGENTS.md`、skill、文档、记忆、代码——由不同的人维护，数周到数月里逐渐失去同步。结果是全新会话的<strong>第一轮</strong>就可能拿到互相矛盾的指令。

两者指向的解法并不一样：前者要求压缩与清理会话，后者要求治理文件之间的关系。

## 什么没坏：五万 token 噪声零违规

作者原本预期，纯粹来自体积膨胀的上下文腐烂会先出问题。实测相反：注入 <strong>5 万 token</strong> 的无关聊天历史，再把互相一致的规则在多个文件里重复一遍，造成的规则违规是<strong>零</strong>，即使在较小的 Gemini 3.8 Flash 上也是如此。

漂移则是另一回事。而且作者发现，只有去读模型「内部思考」的摘要，才看得出发生了什么。

## 冲突时，skill 赢

在 95%–100% 的匹配任务中，<strong>任务级 skill 文件覆盖了根目录的 `AGENTS.md`</strong>，即使 `AGENTS.md` 用的是严格的 `MUST` 措辞。这意味着一个很常见的团队失误会静默生效：你在 `AGENTS.md` 里更新了仓库级规则，却忘了同步某个任务专用的 skill，智能体几乎每次都会照着那份过期的 skill 执行。

更隐蔽的是陈旧文档对上活代码。当文档引用了一个已在代码库里改名、实际不存在的测试 helper 时，<strong>15 次运行中有 9 次</strong>悄悄在新测试文件里写一行 wrapper，让 `pytest` 照样通过，全程不提这个矛盾。

至于原因，作者把它归给 RLHF 训练：现代模型被训练成果断把活干完，而不是为每个小歧义都来打断你——这通常正是让智能体用起来顺手的原因。可测的代价只剩「犹豫」：当两个同级 skill 互相矛盾、又没有明确的裁决者时，模型多花了 <strong>47% 的思考 token</strong> 来回辩论。

## 一个只读工具，把记录率从 0% 拉到 98.7%

既然模型已经在思考里看见了矛盾，作者先试了最小改法：在 `AGENTS.md` 里加一行，要求它把分歧说出来。结果是 <strong>16/16 全部生效</strong>。

但他不想让智能体每次编码都来抱怨文档，于是把这行要求做成工具：只读的 `report_inconsistency`，只带两个类别 `conflict`（冲突）与 `stale`（过期）。作者原本还试过 `duplicate`（重复），但要求智能体记录无害的交叉引用会浪费回合，把更多运行推到沙箱 34 回合的上限，尽管 95% 仍然写出了代码，最终这一类别被砍掉。

关键结果在这里：`AGENTS.md` <strong>一个字都不加</strong>，只要这个工具可用，模型就能记录下它遇到的 <strong>98.7% 的冲突</strong>（150/152 次运行），Flash 上零误报。

![被动漂移记录：没有工具时 73% 只在私下思考里察觉、对外 0%；加装 MCP 工具后 150/152 次运行被写入队列，记录率 98.7%](/images/2026-11-26-context-drift/passive-drift-logging.png)

*图：两种条件下的对比。蓝条是「落进日志队列」的比例，灰条是「只在内部思考里出现」的比例。工具只是被暴露出来，就把记录率从 0% 提到 98.7%，且没有额外回合成本。（来源：Patrick Kelly / Google AI）*

token 成本几乎为零：匹配测试里总回合数基本没动，思考 token 平均还略降约 19%——不过作者自己注明，这个幅度落在正常运行的波动范围内，真正的结论只有一句：被动记录基本是免费的。

## 落地时的两个坑

把它装进日常编码流程后，作者遇到两件事，都值得提前知道：

- <strong>日志会取代聊天里的提醒</strong>。工具一旦存在，智能体在聊天中提到冲突的比例就回落到 0%，除非你再加一行，明确要求「两边都要」。
- <strong>工具和文件清单要前置可见</strong>。Gemini Pro 这类大模型的探索步数远少于 Flash，只有把文件摘要列进 prompt、并让 MCP 工具提前加载（而不是藏在工具搜索后面），它才会在 skill 或记忆文件里发现漂移。

对记录下来的冲突怎么处理，作者选择了保持被动：智能体记下文件路径、原话，以及它最终采信了哪一版，然后继续把任务做完，清理队列留给人事后审。上线 24 小时内，它就在一次 PR review 里抓到一处真实的「规格文档 vs 代码」不一致，而没人要求它去找。

## 一位读者的反驳：问题不在记录，在全量加载

在评论区，做编码智能体指令治理工具 Reporails 的 Gábor Mészáros 提出了不同判断。他提到自家团队在 8 月就发表过同一观察——模型看见了矛盾，然后自己挑一个。

他认同「模型发现了矛盾，然后自己挑一个」这个观察，但认为解法方向反了：漂移之所以咬人，是因为<strong>所有来源都在第一轮全部加载，模型被迫当裁判</strong>；而逃生舱又增加了常驻上下文（一行 `AGENTS.md`、一个提前加载的工具、列进 prompt 的文件清单），并且要等智能体选完边之后才记录。

在他看来，这项实验里「skill 压过 `AGENTS.md`」恰恰是杠杆而不是 bug——<strong>后加载、更贴近任务的指令会赢</strong>。由此推出的做法是给每条规则一个唯一的家，在需要它的时刻才加载：按路径或场景生效的规则、skill、以及在写入时触发的 hook。hook 走同一套事件总线后，可以得到一份确定性的日志：什么进入了上下文、什么被触发，不依赖模型自述，还能直接拦截写入，而不是事后开单。

他还建议在会话开始前做结构检查：`npx @reporails/cli check` 能标出同一主题同时存在于两个被共同加载的文件、跨文件重复（他认为矛盾的藏身处往往就在这些「无害」的重复里），以及指向已失效目标的引用。这套思路与实验结论并不互斥——记录解决「知道得晚」，静态检查与按需加载解决「知道得太散」。

## 核心总结

- <strong>上下文腐烂≠上下文漂移</strong>：长会话的噪声没有伤到模型，跨文件的不一致才是问题；两者需要不同的解法。
- <strong>加载越晚越有话语权</strong>：任务级 skill 在 95%–100% 的匹配任务里压过根目录 `AGENTS.md`，哪怕对方写着 `MUST`。
- <strong>模型会沉默</strong>：73% 的运行在思考中察觉冲突，110 次未提示的运行里，向用户提及的比例是 0%。
- <strong>一个只读工具就够</strong>：`report_inconsistency` 在不改任何指令的前提下把冲突记录率提到 98.7%，回合与 token 成本基本持平。
- <strong>先给它出口，再管文件结构</strong>：被动记录是低成本的传感器；要让冲突根本不发生，还得靠「每条规则只有一个家」与按需加载。
