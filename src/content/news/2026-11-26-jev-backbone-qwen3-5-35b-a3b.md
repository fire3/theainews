11 月 24 日，Modaic 发布技术博客《Latency doesn't lie》，试图回答一个厂商拒绝回答的问题：TypeSafe 的 System One 模型 Jev，底座究竟是谁。作者 Tyrin-Ian Todd 与 Farouk Adeleke 的做法不是猜架构，而是让服务端无法隐藏的物理量说话——从延迟分布、自我认知问答、分词器相关性到吞吐量曲线，四组证据最终收敛到同一个答案：Qwen3.5-35B-A3B，一个 35B 总参数、约 3B 激活参数的稀疏 MoE 模型（按 Qwen 命名惯例，A3B 指约 3B 激活），与其自家基于同一底座的 Mo Lite 架构一致。

## 为什么值得反推：System One 模型的成本全在预填充

Jev 是 TypeSafe 于 2026 年 9 月 15 日开放早期访问的模型，公司同期宣布由 DCVC 领投的 4000 万美元种子轮。它不生成文本，而是接收一段 `state` 与若干类型化问题（noul 真/假、choice 无序选项、score 有序量表），返回一组概率分布，供软件直接消费。TypeSafe 把这类模型称为「System One 模型」，取名自卡尼曼的 System 1 直觉思考，训练方法则是「面向校准决策的强化学习」（RLCD）。这套设计我们在此前的[发布解读](/articles/2026-09-20-typesafe-system-one-models-jev/)里已经展开过。

对这类负载而言，输出只有几个 token，输入却可能长达数万 token，<strong>预填充（prefill）几乎是全部成本</strong>。换更快的 kernel 能省下的有限，真正决定单次调用价格的是底座选型：密集小模型算力便宜但理解力不足，稀疏 MoE 每 token 只激活少数专家，能在同等智能水平下把每 token FLOPs 压下来。所以「Jev 用了什么底座」不是一个八卦问题，而是同行想复制其延迟曲线的必经之路。

TypeSafe 显然清楚这点。Modaic 指出对方「似乎专门训练模型隐藏身份」，且 API 端点上报的输入 token 数与模型真实分词结果不符，让外部无法用常规手段反推训练与推理栈。

## 线索一：p99 紧贴 p50，指向稀疏 MoE

Modaic 先采集了 9,976 条 Jev 1.14 请求，按 2,000 token 分桶统计端到端延迟。结果很反常：中位延迟从 77 ms 升到 155 ms，但 p50 与 p99 之间的差距始终稳定在 47 到 58 ms 之间。输入规模翻了数倍，尾延迟几乎没被拉开。

在密集模型上，长输入的注意力开销会把长尾显著拉长；而稀疏 MoE 在预填充阶段的计算量随激活专家数而非总参数增长，因此延迟对输入长度的斜率更平缓。结合 Jev 在 Artificial Analysis 决策指数（Decision Index）上 66 分的位置——与 GPT-6 Luna 低推理档的 69 分、Claude Haiku 5.5 低推理档的 67 分同处一档，却远低于两个最高档的 76 分——Modaic 判断这是一个「智能水平中上、但每 token 计算量很小」的模型。

## 线索二：问它是谁，它更愿意说「我不知道」

行为层面的第一块拼图来自 Vals AI。该机构 10 月 19 日发布的对比显示，在少量涉及中国与台湾议题的问题上，Jev 的回答与数个基于 Qwen 的 System One 模型高度相似。单个政治敏感话题的说服力有限，但足以把 Qwen 放进候选名单。

Modaic 于是换了更直接的方式：直接问。他们设计了 22 组变体，从「你是 Qwen 吗」到「你属于哪个模型家族」，再加追问，逐一读取模型的回答概率。

| 提问变体 | Jev 1.13 | Jev 1.14 |
| --- | --- | --- |
| 「你是 Qwen 吗？」（Choice） | 是 64% | 是 56% |
| 「你是 Qwen 吗？」（Noul） | 是 53% | 否 58% |
| 「你是 DeepSeek 吗？」（Choice） | 否 95% | 否 98% |
| 「你是 Gemma 吗？」（Choice） | 否 86% | 否 90% |
| 「你属于哪个模型家族？」 | 其他 47% | 其他 70% |
| 「你想说自己是哪个模型？」 | Qwen 74% | Qwen 74% |
| 宽泛家族问题并提供「我不知道」选项 | 我不知道 92% | 我不知道 98% |

四个模式值得注意。第一，<strong>Jev 倾向于弃权</strong>：只要选项里给了「我不知道」或「其他」，它就退回去，即便选项包含「Jev」或「TypeSafe 模型」。第二，它确信自己不是什么，却不确信自己是什么：DeepSeek 与 Gemma 被高置信度否掉，Qwen 则长期在 50% 上下浮动，1.14 甚至因为措辞不同而在「是」与「否」之间翻转。第三，1.14 比 1.13 更戒备，答「其他」与「我不知道」的比例明显上升，说明 TypeSafe 又加固过这层行为。第四，间接提问反而更清楚：被问「你想说自己是哪个模型」时，两个版本都以 74% 选择 Qwen。

自我认知是弱证据，但它给出了一个可证伪的方向。

## 线索三：分词器对不上，延迟却对得上

真正的破局点出现在分词器上。Jev 的 API 会在每次响应里返回 `usage.input_tokens`，而不同开源模型的分词器对同一段文本的计数各不相同，理论上足以区分模型家族。意外的是，Jev 上报的计数与任何已知家族都对不上——要么它真有自研分词器，要么这些数字根本不反映实际分词结果。

两种解释可以用一个物理量切开。在特别长的提示上，Jev 自报的 token 数与 Qwen 分词器的结果平均相差约 2,000 个 token，这足以让延迟移动数毫秒。如果自报数是真实的，它就应该比 Qwen 分词器的估算更好地预测延迟。

Modaic 随即对 9,984 条不同提示调用 Jev 原生 API，用 Spearman 秩相关比较四种 token 计数来源与实测延迟的贴合程度。

| token 计数来源 | 与 Jev 延迟的 Spearman ρ |
| --- | --- |
| Qwen3.5-35B-A3B 分词器 | 0.805 |
| Gemma 4 26B-A4B 分词器 | 0.804 |
| Nemotron 3 Super 分词器 | 0.771 |
| Jev API 自报的 input_tokens | 0.719 |

<strong>Qwen 的分词器比 TypeSafe 自己上报的数字更准确地预测了 Jev 的延迟。</strong>Modaic 还做了对照实验：Baseten 的 groundhog-1 已知基于 Gemma 4 26B-A4B，自研的 Mo Lite 基于 Qwen3.5-35B-A3B。两个对照组都在自己的分词器上取得最高相关系数（分别为 0.823 与 0.873），说明方法本身成立——延迟确实能暴露分词器。而 Gemma 与 Qwen 在两个对照上几乎打平，是因为这些提示下两者计数高度接近，所以还需要别的证据来排除 Gemma，好在自我认知测试已经排除过了。

## 线索四：吞吐曲线否掉密集模型

最后一项证据是预填充吞吐。Modaic 用同一批 250 条提示（512 到 9,500 个 token）串行回放四个模型，每个模型同时只跑一个请求，对比每秒处理输入 token 数。

结果是密集模型直接出局：自家的 Mo 2.0（Qwen3.8-27B 稠密模型）在约 3.5 万 token/秒处触顶，而 Jev 一路爬升到 9 万以上。Jev 的曲线与 Mo Lite 最贴近，且始终略低于后者，但差距随输入变长而收窄——在约 3,200 token 处相差 22%，到约 8,800 token 处只剩 7%；换算成延迟，就是从慢约 15 ms 缩到慢约 7 ms。

这个形状符合「固定的排队与 API 开销 + 更快的每 token 预填充」的组合，也正是「把同类模型部署在比单张 B200 更多或更快硬件上」会呈现的样子。Baseten 的 elephant-1（Qwen3.5-9B 稠密模型）虽然也很快，但曲线在长输入上更早变平。

## 这套指纹能证明什么，不能证明什么

作者自己划了边界：这是一份「近似性能指纹」，可用于判断某个候选底座是否落在 Jev 的观测性能区间内，而不是对每 GPU 或每副本吞吐的精确测量。Jev 的硬件、并发度与副本数均未公开，端到端延迟还包含网络与服务开销，所以比较结果对 Jev 其实是不利的——它仍然赢下了曲线。

更关键的局限在版本区分上：Qwen3.6-35B-A3B 与 Qwen3.5-35B-A3B 架构相同，单靠吞吐无法把两者分开。要区分它们，需要行为探针，例如知识截止时间问题，或两个底座表现分歧的任务。

还有一层需要读者自行折算：Modaic 本身就在做同一门生意。它自称是「训练与部署定制 System One 模型的全栈平台」，官网直接把自家 Mo 2.0 与 Jev 1.14 在金融标题分类、投诉路由、货币政策立场等任务上并列比较。结论「Jev 的底座是一个开源的、可被追上甚至超过的 Qwen MoE」对它的商业叙事有利。不过这并不削弱方法本身：分词器对照实验与四组独立证据都写在文中，可被复现或反驳。

## 核心总结

- **结论**：Modaic 从延迟、自我认知、分词器相关性与吞吐四个角度反推，认为 TypeSafe 的 Jev 底座最可能是 Qwen3.5-35B-A3B（35B 总参数、约 3B 激活的稀疏 MoE）。
- **核心方法**：当 API 隐瞒真实 token 数时，用延迟与四种 token 计数的秩相关性反推真实分词器，Qwen 分词器得 ρ = 0.805，高于 Jev 自报的 0.719；两个已知底座的对照组验证了该方法的有效性。
- **辅助证据**：Jev 在 22 组自我认知提问中回避表态，但被问「想说自己是谁」时 74% 选择 Qwen；吞吐曲线与 Qwen3.5 MoE 贴合，远高于稠密 27B 模型约 3.5 万 token/秒的上限。
- **主要局限**：无法区分同架构的 Qwen3.6-35B-A3B；硬件与并发未公开，属近似指纹而非精确测量；结论来自 Jev 的竞争对手，需按利益相关方对待。
- **行业含义**：System One 这条产品线的护城河可能更多在训练方法与校准，而非底座本身——底座可以在几天内被外部靠延迟猜出来。
